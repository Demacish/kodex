# 0006. Procrastinate for background jobs

Status: Accepted (implemented in phase 2)

## Context

v1 uses Redis/RQ with six queues, one worker and an in-process scheduler
thread that breaks with several replicas. Considered: Celery, Dramatiq, arq
(maintenance mode), Hatchet, pgqueuer, Procrastinate.

## Decision

Procrastinate 3.10: PostgreSQL-backed, async, periodic jobs deduplicated in
the database across workers, retries, locks and priorities. Its schema
migrations are sequenced in Alembic. pgqueuer 1.6 is the fallback behind the
same internal interface. Rate limiters move into the database.

## Consequences

Redis goes away. Procrastinate is looking for maintainers, hence the interface
and the named fallback.

## Implementation notes (phase 2)

`kodex.jobs` is the internal interface: `Queue(name).enqueue(function,
*args, job_id=...)` keeps v1's call shape (positional arguments become the
task's JSON keyword arguments, `job_id` a queueing lock), and `fetch_job` /
`list_jobs` read Procrastinate's tables. Tasks are registered under their
function names and run through a wrapper that stores the return value or
error in `job_results`, which Procrastinate doesn't keep. Enqueueing from
synchronous code goes through a second app on `SyncPsycopgConnector`, by
task name. The schema of Procrastinate 3.10.0 is vendored next to Alembic
migration 0005; a later release's migration files each get an Alembic
migration. The worker runs one job at a time (the tasks are synchronous);
more parallelism means more worker containers. RQ's per-job timeout has no
equivalent. Periodic jobs: library polling every ten minutes, the weekly
release check, and a nightly cleanup of ended jobs.
